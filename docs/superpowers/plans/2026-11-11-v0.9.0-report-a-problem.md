# 0.9.0 Report a Problem Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Ship 0.9.0. Statutory imported pins show their status as fixed by law. Signed-in users can report problems with imported pins. The owner resolves each report with one workflow run, and removed pins stay gone from the database, from later imports and from devices.

**Architecture:**
- **Database.** One additive migration (014) does four things:
  - extends `pin_reports` with reasons, a pin snapshot, outcomes and limits;
  - stops reports from being deleted along with their pin;
  - adds a service-role-only do-not-import table;
  - adds one `resolve_pin_report` database function, which does every resolution in a single transaction.
- **Around the database.**
  - A manual GitHub workflow calls that function over REST.
  - The importer reads the do-not-import table into dedup.
  - The health check learns about report removals and stale reports.
  - The moderation email learns about imported pins.
- **The app.**
  - The pin dialog locks status and tag on statutory pins.
  - The report dialog gains imported-pin reasons.
  - Reported pins are remembered on the device.
  - The viewport cache drops pins the server no longer returns.

**Tech Stack:**
- **App:** Flutter 3.41.7 / Dart 3.11.5, drift, shared_preferences, supabase_flutter.
- **Database:** Postgres/PostGIS via Supabase migrations.
- **Importer:** Python 3.12 importer, using pydantic 2, shapely 2, rapidfuzz, httpx and pytest-httpx.
- **CI scripts:** Python stdlib scripts in `ci/`.
- **Email:** Deno Edge Function.
- **Automation:** GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-11-11-v0.9.0-report-a-problem-design.md`

## Spec refinements (deliberate departures; owner reviews these with the plan)

1. **The do-not-import list matches only direct neighbours, not chains (spec §4.6 said transitive).**
   - **Why:** GSA names are composed `{use} — {city}, {ST}`, so a whole downtown of offices shares one name. A transitive walk in 100 m hops could hide many real red pins, which is the spec's first anti-goal.
   - **What drops:** a candidate is dropped when it has the entry's record id, or is the same source within 100 m with name similarity ≥ 70 to the entry.
   - **Cost if wrong:** a sibling record more than one hop away can reappear as a new pin near the removed one, and a second report removes it.
2. **The do-not-import list never drops a candidate whose key already has a pin.** That would turn the pin into an orphan, and `--delete-orphans` would then delete it. This enforces the spec's "suppression never deletes anything by itself".
3. **A "complete" street-zoom response means `zoom >= 12` with no clusters in it.**
   - The pins-in-view query returns clusters instead of pins whenever more than 2,000 pins are in view. A pin response is therefore never truncated, and a cluster response is the "capped" case.
   - `kClusterCutoverZoom` moves from `lib/presentation/map/pin_visibility.dart` to `lib/core/map_constants.dart`, so the data layer can use it without importing from presentation.
4. **The migration dismisses older duplicate open reports.** For each (pin, reporter) pair it keeps only the newest open report and marks the rest `dismissed`. This has to run before the one-open-report index can be built: prod's 4 smoke-test reports sit on one pin.
5. **The server sets `reporter_id` from `auth.uid()` on insert.** A client can't spoof it to dodge the daily limit.
6. **The moderation email has no automated test.** No CI job runs Deno. It is verified by the staging end-to-end run in Task 11.

  The rules for `resolve_pin_report` (spec §4.5):
  - **Checks.** Lock the report row `FOR UPDATE`. Missing raises `report_not_found`; resolved raises `report_already_resolved`.
  - **Imported.** The pin counts as imported when `COALESCE(pins.created_by, report.pin_created_by)` is the system UUID. Otherwise raise `not_an_imported_pin`.
  - **Which reports close.** Remove closes every open report on that `pin_id`. Move and dismiss close the open reports on that `pin_id` with the same `reason`. All of them get `resolved_at = now()` and the action's resolution.
  - **remove.**
    - Insert into `import_suppressions` with `ON CONFLICT DO NOTHING`. Take source, id, name and coordinates from the live pin, or from the report snapshot when the pin is gone. A NULL id raises `missing_source_external_id`.
    - Then `DELETE FROM pins WHERE id = …`. `pin_deleted` is true when a row was deleted.
  - **move.**
    - Both coordinates are required (`move_needs_coordinates`), and they must be inside the box (`coordinates_outside_continental_us`). The pin must exist (`pin_not_found`).
    - `UPDATE pins SET latitude, longitude, user_modified = true`. A service-role write never sets `user_modified` on its own (013), so the function sets it explicitly.
    - Store `moved_to_*`.
  - **dismiss.** Leave the pin untouched. It works even when the pin is gone.
  - **Anything else** raises `unknown_action`.

  Add a header comment explaining two things:
  - why the FK was dropped (spec §4.3);
  - that `now()` is the same in the `pin_deletions` row and in `resolved_at`, because both are written in one transaction. The health check relies on this (Task 3).

### Task 4: Resolve pin report workflow

**Files:**

**Interfaces:**

  - `@dataclass(frozen=True) class ResolveRequest`: `target: str`, `report_id: str`, `action: str`, `latitude: float | None`, `longitude: float | None`.
  - `class InputError(Exception)` and `class ResolveError(Exception)`.
  - `validate_inputs(*, target, confirm, ref, report_id, action, latitude, longitude) -> ResolveRequest`, where every argument is a `str`. It checks:
    - `ref == "refs/heads/master"`;
    - `confirm == f"I-KNOW-THIS-WRITES-TO-{target.upper()}"`;

    - a move has both coordinates inside the box, and any other action has neither.

  - `check_key(target: str, key: str) -> None`: raises `InputError` when the key is empty or its `ref` isn't `PROJECT_REFS[target]`.
  - `call_resolve(req: ResolveRequest, key: str, post=_http_post) -> dict`: POSTs `https://{ref}.supabase.co/rest/v1/rpc/resolve_pin_report` with `{"p_report_id", "p_action", "p_latitude", "p_longitude"}`. A non-2xx response raises `ResolveError(<PostgREST message>)`.
  - `render_summary(req, result: dict) -> str`: markdown for `$GITHUB_STEP_SUMMARY`.
  - `main() -> int`: reads `TARGET, CONFIRM, REPORT_ID, ACTION, LATITUDE, LONGITUDE, GITHUB_REF` and `KEY_ENV[target]` from the environment. It returns 0 on success and 1 on any error, printing `::error::<message>`.
