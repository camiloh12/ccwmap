# 0.9.0: locked statutory pins and "Report a problem" on imported pins

**Status:** design, awaiting owner review (2026-11-11)
**Owner decisions:** 2026-09-27 (pilot close-out) and 2026-11-11 (this conversation)
**Related:** BUG-006 / migrations 012–013 (`CLAUDE.md`), Phase 8a
(`2026-10-26-phase8a-national-federal-wave-design.md`), daily health check
(`2026-09-27-daily-health-check-design.md`), release playbook
(`docs/dev/GIT_FLOW.md`)

## 1. Why

Prod holds 38,281 imported pins across the 48 contiguous states plus DC.
Users can't fix the ones that are wrong:

- They can't delete imported pins (012), and they can't change the status,
  tag or location of statutory ones (013, `confidence = 'high'`). The app
  still offers those changes: the save looks fine, the server keeps the old
  values, and the change reverts on the next fetch. Every shipped version
  has this gap.
- The Report button is hidden on imported pins (`isOtherUserPin` in
  `map_screen.dart` excludes the system user). So there is no channel at
  all. Zero reports in seven months means nothing.
- Phase 8a added 15,550 medium-confidence GSA and National Guard pins.
  Some are closed offices or sit in the wrong spot, and the FRPP coordinate
  cross-check was dropped on purpose (identity-and-cleanup spec), leaving
  outliers to this flow.

The BUG-006 client fixes (commit c8f4ebc) have also sat unreleased on
`master` since 2026-09-26, and the held 0.8.1 release needs cleaning up.

## 2. Goals, non-goals, anti-goals

**Goals**
1. A statutory imported pin shows its status and tag as fixed by law, with
   the citation, and the app never offers a change the server will discard.
2. A signed-in user can report a problem with any imported pin in a few
   taps, choosing a reason that fits imported data.
3. The owner gets each report by email with everything needed to decide,
   and resolves it with one GitHub Actions run: **remove**, **move** or
   **dismiss**.
4. A removed pin stays gone: later imports don't bring it back.
5. Every outcome is recorded, and the daily health check neither
   false-alarms on owner removals nor lets other deletions slip by.
6. Ship BUG-006's client half and retire the held 0.8.1.
7. A pin deleted on the server leaves a device's map the next time that
   device loads the area at street zoom. This covers owner removals and
   the importer's own deletions, including the ones already made.

**Non-goals**
- An in-app admin or triage screen (option B, rejected).
- Anything that hides or changes a pin without the owner deciding
  (option C, rejected): no vote counts, no auto-hide.
- Telling the reporter the outcome. Their "Reported" mark stays on their
  device.
- Reports from guests. Reporting stays signed-in only, as today.
- Changing how reports on user-created pins work (same reasons, same
  email, owner handles them in Studio as today).
- Letting users delete imported pins (012 stands).
- Owner actions beyond remove/move/dismiss, e.g. downgrading a pin to
  UNCERTAIN or renaming it. Users can already rename imported pins.
- A map picker for "wrong location". The note carries where it really is.

**Anti-goals** (failure even if it works)
- A real gun-free pin hidden or removed without the owner deciding.
- A removed pin back on the map after the next import.
- A removed pin still showing on a 0.9.0 device that has reloaded that
  area at street zoom.
- A user's own pin, or a pin with an edit waiting to upload, dropped from
  the device by the new cache cleanup.
- A reporter's note or account id in a public GitHub Actions log (the repo
  is public).
- A locked field that looks editable, or a save that looks successful and
  then reverts.
- The health check going red because the owner resolved a report, or
  staying green after a deletion nobody accounts for.

## 3. What exists today (checked 2026-11-11)

- `pin_reports` (005): `pin_id` FK to `pins` with **ON DELETE CASCADE**,
  `reporter_id`, `reason` CHECK in `INACCURATE/OFFENSIVE/SPAM/OTHER`,
  `note` ≤ 500 chars, `created_at`. Insert for `authenticated`, no read
  policy (service role only). Prod has 4 rows, all 2026-04 smoke tests.
- A database webhook on `pin_reports` INSERT calls the
  `send-moderation-email` Edge Function, which emails pin id, reporter id,
  reason, note and Studio links through Brevo. Nothing in CI deploys Edge
  Functions; they are deployed by hand.
- `PinDialog` takes `onReport` / `onBlock`, already receives `source`,
  `confidence`, `legalCitation`, `legalCitationVerifiedDate` and
  `sourceExternalId`, and renders the provenance caveat from
  `pin_provenance.dart`. Status is three tappable options; the tag is a
  dropdown. The dialog has no location field.
- `ReportPinDialog` offers Inaccurate / Offensive / Spam / Other plus a
  note; `ModerationRepository.reportPin` inserts the row.
- 013 keeps `status`, `restriction_tag`, `latitude`, `longitude` on system
  pins with `confidence = 'high'` for `authenticated` sessions. It doesn't
  apply to `service_role` or `postgres`. `set_user_modified` never marks a
  `service_role` write.
- The importer skips `user_modified` rows (`stages/diff.py`). It doesn't
  read `pin_deletions`, and pin ids are random, so a deleted imported pin is
  re-inserted on the next import unless something stops it.
- Health check rules 4 and 5 alert on system-pin deletions outside a
  successful importer apply's `import_runs` window. A service-role delete
  records `deleted_by` NULL.
- The app draws every pin in its local cache (`watchAllPins`). A viewport
  fetch only upserts what the server returns (`upsertCachedPins`,
  insert-or-replace). It never drops cached pins the server no longer has.
  Other people's pins leave the cache only through LRU eviction above
  20,000 rows, or the reset at 2× that. A moved pin does update, because
  the upsert replaces the row whatever its `last_modified`. A pin deleted
  on the server stays on every device that already cached it. That
  includes the importer's own orphan deletions (101 on 2026-10-19 and
  1,912 on 2026-11-02). The pins-in-view query caps its pin branch at
  2,000 rows.

## 4. Design

### 4.1 Pin dialog for imported pins

A pin is **locked** when it was created by the system user and its
confidence is `high`, the same rule 013 enforces. User edits don't unlock
it. For a locked pin:

- The current status shows as selected; the other two options are shown
  disabled. The restriction tag dropdown is disabled.
- Directly under them: *"Set by law (18 U.S.C. § 930). This can't be
  changed here. If it's wrong, use Report a problem."* The citation comes
  from `legalCitation`. With no citation, say "Set by law" alone. Exact
  copy is the builder's, within that meaning.
- Name, posted signage and security screening stay editable and save, as
  013 allows.

Medium-confidence imported pins (GSA offices, National Guard sites, OSM
bars) keep today's editable dialog and orange caveat. User pins are
unchanged.

Every imported pin, locked or not, shows **Report a problem** to
signed-in users. Guests see the read-only dialog without it, as today.
Block stays hidden on imported pins: there is no user to block.

### 4.2 Reporting

Tapping Report a problem on an imported pin opens the report dialog with
reasons for imported data:

| Reason (stored) | Shown as |
|---|---|
| `CLOSED` | Closed or no longer there |
| `WRONG_LOCATION` | Wrong location |
| `NOT_CATEGORY` | Not a *{category}*, e.g. "Not a federal building", "Not a school", phrased from the pin's restriction tag |
| `DUPLICATE` | Duplicate of another pin |
| `OTHER` | Something else |

The note stays optional, 500 characters. Its hint should suggest saying
where the place really is for "wrong location". Reports on user pins keep
the current four reasons.

After a successful submit: a snackbar *"Thanks, we'll check it."* The
button on that pin then reads **Reported** and is disabled on this device.
The mark is stored locally and survives restarts, not reinstalls.

Limits (server-side, so an old or modified client can't skip them):
- One open report per pin per account. A second attempt counts as already
  reported, and the app shows the Reported state, not an error.
- At most 10 reports per account in 24 hours, across all pins. The app
  shows a plain message when this is hit.

The two refusals must be distinguishable by the client (my call):
- The duplicate comes from a unique index on open reports. The app treats
  that unique violation as "already reported".
- The daily limit is raised with its own error code or message, which
  the app maps to the limit text.

Apps before 0.9.0 can only report user pins. They show their generic
error if they hit either limit, which is acceptable at today's volume.

### 4.3 Report records

A new migration extends `pin_reports`. All changes are additive, so apps
before 0.9.0 keep working, and it must reach prod before the 0.9.0 beta
(beta builds talk to prod).

- **Reasons:** the CHECK accepts the five imported-pin reasons alongside
  the current four.
- **Snapshot:** on insert, a trigger copies from the pin (never from the
  client) its `source`, `source_external_id`, `name`, `latitude`,
  `longitude`, `restriction_tag`, `confidence` and `legal_citation`. This
  feeds the email and keeps the record readable after a removal.
- **Survives removal:** deleting a pin no longer deletes its reports. The
  report keeps the removed pin's id, so the health check can match it to
  the `pin_deletions` row.
- **Outcome:** `resolved_at`, `resolution` (`removed` / `moved` /
  `dismissed`), and for a move the new coordinates. Open = `resolved_at`
  is NULL.
- The limits in 4.2.
- Reports stay unreadable to `authenticated` and `anon`.

### 4.4 Email

The existing webhook and function stay. For a report on an imported pin,
the email adds:
- the snapshot: name, the dataset in words (`sourceLabel`), record id,
  tag, confidence, citation;
- a map link at the pin's coordinates;
- the exact values to paste into the resolve workflow: the report id, the
  three actions, and, for a move, the current coordinates as a starting
  point.

The subject makes imported-pin reports easy to tell apart, e.g.
*"[CCW Map] Imported pin reported: Closed (gsa)"*. The email is private,
so the note and reporter id stay in it. Deploying the updated function is
a manual step in the rollout (§6).

### 4.5 Resolving

A new manual workflow, **Resolve pin report** (`workflow_dispatch`):

- **Inputs:** `target` (staging / prod), `report_id`, `action` (remove /
  move / dismiss), `latitude` and `longitude` (move only), and the same
  typed confirmation as `importer-apply.yml` for prod.
- **Shell safety:** inputs reach the script through `env`, never
  interpolated into `run:`. The job checks the service key belongs to the
  target project before any call. This closes the
  silent-fallback-to-staging-key footgun the B2 import hit.
- **The log** shows only the report id, the action, and the pin's public
  facts (name, source, coordinates). Never the note or the reporter.
- **Access** (my call): it calls the function below as a REST RPC with
  the service-role key. It uses the same `PROD_` / `STAGING_SUPABASE_
  SERVICE_ROLE_KEY` secrets and the same confirmation gating as
  `importer-apply.yml`. It needs no direct DB connection and no new
  secret.

The work happens in **one database function**, callable only by
`service_role`, so a resolution can't half-happen.

Which reports it closes (my call):
- **remove** closes every open report on the pin, since the pin is gone.
- **move** and **dismiss** close the named report plus any other open
  report on the same pin with the same reason. A "closed" report on a
  pin you just moved stays open.

The actions:

- **remove:**
  1. Adds the pin's source record to the do-not-import list (§4.6), with
     its snapshot.
  2. Deletes the pin.
  3. Marks the reports `removed`.

  If the pin is already gone (an import removed it), it records the
  outcome and adds the list entry anyway.
- **move:** sets the new coordinates and `user_modified = true`, so
  imports leave it alone. It has to set this flag explicitly, because a
  `service_role` write never sets it. It marks the reports `moved`. It
  refuses coordinates outside the app's continental-US box.

  A moved pin is frozen against later imports, like any user-corrected
  pin. Its confidence and citation stop refreshing too. That is the
  existing "user-corrected pins never receive new confidence/citation"
  follow-up, accepted here, not fixed.
- **dismiss:** marks the reports `dismissed`. The pin is untouched.

The function refuses a report whose pin wasn't imported. Those stay a
Studio task, as today. It also refuses an already-resolved report, and
the workflow says so.

### 4.6 Do-not-import list

A new table, service-role only. Each entry records:
- source and record id;
- name and coordinates;
- the report that created it, and when.

It is permanent until the owner deletes an entry by hand. The runbook
says how.

The importer reads the list once per run and applies it **inside dedup**
(my call). Each entry joins the dedup pass as an invisible member of its
own source. It always wins and is never written, so it takes with it:

- **Same record id:** the candidate with the entry's record id.
- **Its cluster:** every same-source candidate that dedup's match rule
  (100 m and name similarity ≥ 70, transitive) puts in its cluster.

The cluster part is needed because several FRPP rows of one complex fold
into a single pin. Without it, removing the survivor would let a sibling
row, even one matched only through another sibling, become the new
survivor and put the closed building back. It also covers a record
whose id changes upstream.

Entries never suppress other sources. When the owner removes a GSA
duplicate of an airport, the FAA pin must stay.

Dropped candidates are counted as **suppressed** per source in the
dry-run and apply reports. Suppression never deletes anything by itself.

### 4.7 Health check

- **Rules 4 and 5:** they skip a system-pin deletion whose pin id matches
  a report resolved `removed`, deleted within a few minutes of that
  resolution. The digest lists those as *"Removed via reports"*. Any other
  system-pin deletion still alerts.
- **Digest:** it counts `removed` resolutions, so a removal whose pin an
  import had already deleted still shows, just with no deletion to match.
- **New finding:** an imported-pin report that has been open for more than
  7 days. This is a safety net for a missed email, since Brevo has broken
  quietly before. User-pin reports are left out: they are still resolved
  in Studio with no recorded outcome, so they would never close.
- **Digest:** the open-report count and the oldest open report's age. The
  existing `imported_reports_7d` must keep counting reports whose pin was
  removed.

### 4.8 Server deletions reach the device

Owner decision 2026-11-11: fix this in 0.9.0. When a viewport fetch
returns individual pins, the app removes from its cache every pin inside
the fetched box that the server didn't return. "Individual pins" means
the pins-in-view query's street-zoom branch, not clusters.

It only does this when all of these hold:
- The response is complete: fewer than the query's 2,000-row cap. A
  capped response, or a cluster response, cleans up nothing.
- The pin is not the signed-in user's own. The query never returns the
  caller's own pins (`created_by IS DISTINCT FROM auth.uid()`), so they
  are always absent by design. Own pins stay with `MyPinsSync`, which
  already handles their remote deletion.
- The pin has no pending operation in the sync queue.
- The pin lies inside the box that was actually requested, using the
  same edges the server tests.

It also respects the existing request-generation check, so a stale
response never cleans up after a newer one.

This clears the ghosts left by earlier importer deletions on any 0.9.0
device, the first time it loads those areas at street zoom. Apps before
0.9.0 keep their ghosts until they update; nothing server-side can fix
that. The web build's cache is in memory and starts empty on every load,
so it gains little from this, but the same code runs there.

Tests: the rule above as unit tests on the viewport manager. Cover a
removed pin dropped, an own pin kept, a pending-edit pin kept, a capped
response untouched, a cluster response untouched, and a pin outside the
box kept.

## 5. Constraints

- Migrations reach staging and prod only through `db-migrations.yml`.
  They must be idempotent and transaction-safe, and applied ones are never
  edited.
- Schema stays additive: apps before 0.9.0 must keep working against it.
  They will keep sending the old reasons on user pins.
- Supabase MCP stays bound to staging. No prod access outside the
  pipelines and the owner's dashboard.
- Pinned toolchains don't move in this work: Flutter 3.41.7, Supabase CLI
  2.118.0.
- Flutter tests, importer tests (359) and `ci/tests` stay green. New
  logic gets tests where existing patterns allow:
  - the locked-pin rule and the report reasons as pure, unit-tested
    helpers, like `pin_provenance.dart`;
  - suppression matching in the importer suite;
  - the workflow's structure in `ci/tests` / `test_*_workflow.py`;
  - database behaviour through a rolled-back staging probe, like
    `supabase/probes/013_*`.
- No secret is ever printed. Secrets are set from `.local/` files.

## 6. Rollout and acceptance

1. **Migration to staging.** Run a rolled-back probe that shows:
   - the reason CHECK accepts the new values and rejects others;
   - the snapshot is filled from the pin, not the client;
   - a duplicate open report is refused, and the 11th report in 24 h is
     refused;
   - a report survives its pin's deletion;
   - remove, move and dismiss each do exactly §4.5;
   - `authenticated` can't read reports or call the resolve function.
2. **Edge Function to staging.** A test report produces the new email.
3. **End to end on staging**, with a staging-pointed app build:
   1. File a report on an imported pin.
   2. The email arrives.
   3. The workflow removes the pin.
   4. An importer dry-run for that source shows 1 suppressed and 0
      inserts.
   5. A manual health-check run is green and lists the removal.
   6. The same chain for move (the next dry-run skips the pin) and dismiss.
   7. On a staging-pointed device that had the removed pin cached:
      reopening that area at street zoom drops it. A moved pin shows in
      its new spot.
4. **Migration to prod** (owner approval gate), then the Edge Function to
   prod.
5. **Release.** Cut `release/v0.9.0` and beta-test on Android and iOS:
   - a locked pin shows locked fields with the citation;
   - a medium pin stays editable;
   - Report a problem works, and the Reported mark persists;
   - Delete is hidden on imported pins;
   - a rejected save surfaces an error.

   Owner check: a report filed on prod from the beta, then dismissed via
   the workflow.
6. Merge, tag `v0.9.0`, store steps per GIT_FLOW §7, retire 0.8.1.

## 7. Calls made in this document (not owner-stated)

- **Locked pins:** the locked-pin rule mirrors 013 exactly. Block stays
  hidden on imported pins, and medium pins get no change beyond Report.
- **Reasons and limits:** the stored reason names and their wording. One
  open report per pin per account, and 10 per 24 h. The two refusals are
  distinguishable by the client.
- **Report records:** snapshot columns are filled by trigger. Remove
  closes every open report on the pin. Move and dismiss close only
  reports with the same reason.
- **Resolve workflow:**
  - resolution runs in one database function, called over REST RPC with
    the existing service-role secrets;
  - the workflow refuses non-imported pins and checks the key against the
    target;
  - prod needs a typed confirmation;
  - a move is limited to the continental-US box.
- **Do-not-import list:** entries act inside dedup, removing their own
  source's matching cluster, transitively. Removing an already-gone pin
  still adds the entry.
- **Health check:** removals are excluded by matching a resolved report.
  A report open more than 7 days is a finding.
- **Cache cleanup** (the fix is the owner's decision; the conditions are
  mine): it runs only on complete street-zoom responses. It never
  touches own pins, pins with pending edits, or pins outside the
  requested box.
